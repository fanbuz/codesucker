# CodeSucker v0.4.4 Issue Plan — Windows 显示质量与 macOS 原生窗口

## 版本定位

- 里程碑：`v0.4.4 — Windows 字体与缩放质量`
- 版本目标：收敛 Windows 下普通界面、代码/路径混排、显示缩放和申报文档预览的视觉质量，同时让 macOS 恢复原生交通灯与系统窗口行为；通过公开 pre-release 安装包完成双平台实机验收。
- 现有入口：[GitHub #31](https://github.com/fanbuz/codesucker/issues/31)
- 发布策略：先发布 `v0.4.4-rc.1` pre-release；Windows 验收通过后再发布 `v0.4.4` 稳定版。
- 建议负责人：`fanbuz`

## 当前仓库事实

1. 普通界面当前从 `-apple-system`、`PingFang SC` 开始回退，Windows 下最终容易由 `Microsoft YaHei` 同时承担英文、数字和中文。
2. `--mono` 当前以 `ui-monospace`、`SFMono-Regular`、`Menlo` 开头，Windows 只有较后的 `Consolas` 兜底，且没有为中文路径提供明确的 UI 中文字体回退。
3. renderer 中存在较多 `9px`、`9.5px`、`10px`、`10.5px`、`11.5px` 和 `550`、`650`；既有集中 CSS，也有组件内联样式，不能只修改一处全局声明。
4. 第 4 步 A4 页面使用 `SimSun` / `Songti SC` 模拟申报文档；导出链路明确写入 `SimSun`、`10.5pt` 和固定行距。这一字体域不应随普通 UI 字体栈一起调整。
5. GitHub Actions 已能在 `windows-2022` 构建 NSIS 并做启动 smoke；带预发布标识的 tag 会自动创建 GitHub pre-release，但 CI 不能替代真实 Windows 字体、缩放与 Word 检查。

## 范围

### In scope

1. 为普通 UI、代码/路径/统计、申报文档建立彼此独立的字体 token 与平台回退规则。
2. Windows 普通 UI 使用 `Segoe UI Variable` / `Segoe UI` / `Microsoft YaHei UI`；macOS 保持系统字体表现。
3. Windows 代码、路径和统计优先使用 `Cascadia Mono`，依次回退到 `Microsoft YaHei UI`、`Consolas` 和通用等宽字体。
4. 普通 UI 文本字重收敛到 `400`、`500`、`600`；清理 `550`、`650` 等容易触发合成加粗的字重。
5. 将承载操作、状态、路径、校验结论或决策提示的关键辅助信息提升到至少 `11px`；装饰性标记和按比例模拟的 A4 内容单独判断，不机械全局放大。
6. 在 Windows 100%、125%、150%、200% 显示缩放下验证两种目标窗口尺寸、长中英文路径、20 种以上文件类型和暗色模式。
7. 单独验证 Windows 下 A4 宋体预览、实际 DOCX 的字体声明、Word 打开效果、页眉、固定行距和分页结果。
8. 通过 `v0.4.4-rc.1` 安装包收集 Windows 实机截图与结论；如有阻断问题，递增 `rc.2`、`rc.3`，不覆盖既有 tag 或 Release。
9. macOS 使用原生 `hiddenInset` 标题栏与左上角交通灯，隐藏右上角自绘窗口按钮，并验证系统全屏、标题栏双击缩放、吸附与多显示器行为。

### Out of scope

- 不改变清洗、选行、分页、截取或导出内容语义。
- 不修改每页 50 行、正文 10.5pt、宋体、页眉或固定行距等申报规则；若实机验证发现规则本身需要变化，应另建 issue，并评估是否更新 `RULES_VERSION`。
- 不引入自带字体文件，不处理字体授权与安装包体积变化。
- 不承诺用 macOS 截图或浏览器模拟代替 Windows 实机验收。
- 不在本版处理 Linux 字体栈、macOS 签名/公证或 Windows 代码签名。

### 建议标题

`v0.4.4：Windows 字体、显示缩放与申报文档质量验收`

### 目标

在 Windows x64 上建立清晰、稳定且可验证的字体与布局基线：普通界面不因中文回退整体显得偏粗偏挤，代码与路径中英文混排可读，关键辅助信息在高 DPI 下不发灰，申报文档预览与 Word 导出保持既定宋体排版。

- [ ] 普通 UI 与等宽字体栈实现并完成自动化约束。
- [ ] 关键辅助字号、文本字重和缩放布局完成收敛。
- [ ] A4 预览与 DOCX/Word 结果完成独立验证。

- [ ] 普通 UI 的英文、数字、中文没有异常粗细跳变，输入框、按钮和系统控件继承同一平台字体策略。
- [ ] 代码、路径和统计在 Cascadia Mono 存在与不存在两种情况下均有明确、可读的回退结果；中文字符不显示方框或异常基线。

## 子 Issue 草稿 1：Windows 普通 UI 与等宽字体基线

### 目标与范围

- 建立 `--font-ui`、`--font-mono`、`--font-document` 三个明确字体域，避免文档宋体规则泄漏到 UI，也避免 UI 调整影响文档。
- 让 renderer 能确定当前平台，并通过根元素属性或 class 选择 Windows/macOS 字体 token；平台信息只用于展示层，不扩大 IPC 权限。
- Windows UI 栈：`"Segoe UI Variable", "Segoe UI", "Microsoft YaHei UI", sans-serif`。
- Windows mono 栈：`"Cascadia Mono", "Microsoft YaHei UI", Consolas, monospace`。
- macOS UI 继续使用系统字体；macOS mono 保持系统等宽优先。
- 输入框、按钮、SVG 统计文字、代码、路径、页数和文件类型统计全部使用对应 token，不保留散落的独立平台字体声明。
- 增加静态测试，至少约束三类 token、Windows 回退顺序、平台标记和 `SimSun` 只能存在于文档字体域/导出配置。

### 验收标准

- Windows 11 上普通 UI 优先命中 Segoe UI Variable；Windows 10 或字体缺失时稳定回退到 Segoe UI / Microsoft YaHei UI。
- Cascadia Mono 存在时英文、数字优先命中该字体，中文字符按定义回退；缺失时不出现方框、错位或不可读混排。
- macOS 与 v0.4.3 的系统字体观感无明显回退。
- A4 预览与 DOCX 导出的宋体、字号和分页结果不因本 issue 改变。

## 子 Issue 草稿 2：Windows 字号、字重与布局缩放回归

### 目标与范围

- 盘点集中 CSS 与 React 内联样式中的文本规格，将普通 UI 文本字重收敛到 `400`、`500`、`600`。
- 把 `550`、`650` 映射到最接近的标准档；文字型 `700` 逐项判断，默认降到 `600`，纯图形/勾选符号不纳入正文限制。
- 将关键辅助信息提升到至少 `11px`；关键范围包括路径、扫描/导出状态、错误与警告、操作提示、统计说明、可点击筛选及设置规则说明。
- `9px`—`10.5px` 只允许保留在不承担关键决策的装饰徽标、缩略页标记或 A4 比例模拟中，并在代码旁体现其语义分类，避免后续再次扩散。
- 回归第 2 步的目录树、排序列表、统计面板、20+ 文件类型列表和底部“下一步”；同时 smoke 其他页面与设置页。

### 验收标准

- 普通 UI 不存在 `font-weight: 550`、`650` 或等价内联值；关键辅助信息不存在低于 `11px` 的声明。
- 100%、125%、150%、200% 下字形不发灰、行高不挤压、按钮标签不裁切、焦点态不偏移。
- `1160 × 760` 和 `1440 × 900` 下核心操作区始终可达；长路径和 20+ 文件类型不引入横向撑破、双重滚动或底部按钮消失。
- 亮色与暗色下文本对比、禁用态、提示态和错误态仍可辨认。

## 子 Issue 草稿 3：Windows 申报文档预览与 Word 导出一致性

### 目标与范围

- 将第 4 步 A4 页面明确标记为“申报文档预览”字体域，继续使用宋体优先，不套用普通 UI 的最小字号规则。
- 用同一份混合样本贯通预览、分页和 DOCX：中文软件名、中文文件名、英文路径、数字、常见代码符号、长行和页眉。
- 自动检查 DOCX 包内字体声明、字号、固定行距、页眉与页码结构；人工使用 Windows 桌面版 Word 检查实际渲染和分页。
- 比较 A4 预览与 Word 的语义一致性；允许预览因等比例缩小产生 CSS 像素差异，不要求逐像素一致。

### 验收标准

- Windows 中 A4 预览可正常命中 SimSun，中文、英文、数字和符号无缺字、重叠或异常基线。
- 导出 DOCX 的正文保持 SimSun 10.5pt 和当前固定行距；页眉、页码、50 行分页及总页数符合当前规则。
- 在 100%、125%、150%、200% 显示缩放下，预览纸张、页眉、代码区、翻页按钮和缩略页操作区互不遮挡。
- Word 实机证据包含字体面板或样式信息、页眉、正文行距和至少一处分页边界。
- 如预览与 Word 不一致，必须判断是视觉模拟误差还是导出缺陷；导出缺陷阻断稳定版。

## 子 Issue #65：feat(macOS): 恢复原生交通灯与窗口行为

### 目标与范围

- macOS BrowserWindow 使用原生 `hiddenInset` 标题栏和左上角红黄绿交通灯；Windows 保持现有无边框自绘窗口。
- macOS 隐藏右上角自绘最小化、最大化和关闭按钮，为交通灯保留安全空间。
- 标题栏空白区域保持可拖拽，按钮、链接和其他交互控件区域必须不可拖拽。
- 继续复用现有窗口尺寸、位置、最大化状态和外接显示器恢复逻辑。
- 增加主进程窗口选项、renderer 控件可见性和拖拽区域的自动化约束。

### 验收标准

- macOS 左上角显示原生交通灯，右上角不显示自绘窗口按钮，深浅色与最小窗口下无重叠。
- 绿灯全屏、双击标题栏缩放、窗口吸附和系统窗口菜单行为正常。
- 刘海屏与外接显示器环境下交通灯、品牌标题和工具栏互不遮挡，窗口恢复后仍处于可见工作区。
- macOS arm64 与 x64 安装包均完成启动与窗口操作实机冒烟。
- Windows 自绘窗口按钮和现有窗口行为无回归。

## 依赖、风险与门禁

1. 字体栈改变会重新分配文本宽度，因此布局验收必须在字体基线合入后执行，不能复用 v0.4.3 截图作为结论。
2. Windows 字体是否命中不能只靠 CSS 字符串推断；实机需记录 Cascadia Mono、Segoe UI Variable 是否安装，并使用开发者工具字体面板或等价证据确认。
3. Electron 窗口尺寸使用逻辑坐标。证据中要同时记录显示器原始分辨率、系统缩放和应用窗口逻辑尺寸，避免把物理像素与 CSS/DIP 混为一谈。
4. 提升辅助字号可能在 `1160 × 760` 触发布局回归；优先调整容器、间距、换行和滚动，不以重新缩小字体掩盖问题。
5. `v0.4.4-rc.1` 只代表可供 Windows 验收，不代表 `#31` 完成；CI 构建成功和进程能启动也不能替代人工视觉与 Word 验收。
6. 稳定版门禁：四个工作包验收通过、`#31` 证据齐全、`npm run verify` 通过、Windows NSIS 安装/启动/真实项目扫描/导出通过，macOS arm64/x64 原生窗口冒烟通过。

## Pre-release 与稳定版节奏

1. 完成四个工作包中可在本机和 CI 上验证的实现、静态约束、DOCX 结构测试与基础回归。
2. 将版本统一设置为 `0.4.4-rc.1`，整理对应 CHANGELOG，运行 `npm run verify`。
3. 创建并推送 annotated tag `v0.4.4-rc.1`；现有 Release workflow 自动构建 Windows x64 NSIS 并创建 pre-release。
4. 在真实 Windows 上按统一矩阵执行；每个失败项记录环境、步骤、期望、实际和截图。
5. 阻断缺陷修复后发布递增 RC；已发布的 RC tag 和资产不覆盖、不移动。
6. Windows 矩阵通过后，将版本设置为 `0.4.4`，补齐稳定版 CHANGELOG、README 下载版本与路线图，完成最终验证并发布稳定版。
